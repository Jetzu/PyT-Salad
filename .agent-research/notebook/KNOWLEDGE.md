# Knowledge

## Headline
- K014: a JAX fixture generated on GPU is NOT an fp32 reference (XLA:GPU lowers `dot` to TF32 unless `jax_default_matmul_precision="highest"`); this looked like a 300-1800x port bug (R001) and was purely a fixture-generation artifact. Always pin `highest` and record backend+precision provenance in every fixture.
- R001 (refuted K013): "default_vp_scaled/multimotif_vp are 300-1800x looser than default_vp" was never a property of those configs — both fixtures were GPU-generated (K014). Lesson: an anomalously large, config-specific parity gap with an otherwise-clean signal (exact `aatype`) is a strong hint to check fixture provenance before hypothesizing about the model.
- K015: the SALAD denoiser trunk is CONTRACTIVE, not chaotic (~1e-5 in -> ~1e-5 out; neighbour index arrays are bit-stable across backends). A >=1e-3 A parity gap can never be "fp32 noise amplified" in this model — it is always a discrete or precision-class difference. Load-bearing for every future parity investigation.
- K012: never compare post-Adam-step parameter deltas element-wise as a parity check, even with near-exact gradients — Adam's update is `sign(g)*lr` per element at t=1, so ordinary fp32 noise on near-zero gradients flips signs and produces spurious full-LR discrepancies. Compare gradient cosine/norm instead.
- K011: full training-step parity confirmed end to end — whole-model gradient cosine 0.99999863 vs JAX (real weights, real loss), and `optax`'s Adam chain is mathematically identical to `torch.optim.Adam` with matched hyperparameters.
- K010: `AADecoder.train_forward`'s ADM-masking RNG (threefry vs torch `Generator`) cannot be made to match JAX bit-for-bit and contaminates gradients for UNRELATED trunk parameters if left uncontrolled. Fix for any exact cross-backend training check: force `aa_gt` all-MASK, which short-circuits the draw deterministically (costs the aa/x/violation/local terms, which go to exactly 0).
- K002: the Encoder is numerically EXACT vs upstream on real weights (coords max 0.00001 A) — the only Encoder defect class was the indexing crash (K001/K009), not the math.
- K009 / K001: `Rigid.__getitem__` was removed but 5 call sites across `encoder.py`, `losses/structure.py`, `losses/total.py` still indexed it directly — `load_state_dict(strict=True)` passing proves nothing about whether a forward/training pass can even run. All 5 fixed in N004; verify indexing-style call sites by hand whenever a helper class's API changes shape.
- K005: symmetry's clash-repulsion gradient clamps the SQUARE instead of the DIFFERENCE (`chain_center` hook) — found independently twice (N003, N010/S7). Still open (TODO T5).
- K007: `--seed` does not make a design reproducible — `inference/options.py` uses unseeded stdlib `random` (15-25 A swing on `--dssp random`) and the Gumbel neighbour draw uses the process-global RNG. Still open (TODO T6).

- K012: gotcha [verified] Do NOT compare POST-Adam-step parameter deltas element-wise at step 1 (or generally) as a parity check, even when gradients match near-exactly. Adam's update is `m_hat/(sqrt(v_hat)+eps)`; at t=1 bias correction is exact (`m_hat=g`, `v_hat=g^2`), so update = `sign(g)*lr` PER ELEMENT regardless of `|g|`. An element with a near-zero true gradient has its sign set by ordinary fp32 noise, which Adam then amplifies into a full +-lr discrepancy — verified directly on 4 example parameters (cosine 0.9998-1.0 on the raw gradient; one near-zero coordinate flips sign in the post-step delta, `peak|ref_delta|` conspicuously exactly the LR). Compare gradients (cosine/norm), not post-step weights. (N004; results/N004-porting-gaps/task3_check_gradstep.py) {cites:1}

Two H100 runs of the same config at default precision also differ from each other by 4.47e-03 A (autotuner kernel choice), so GPU fixtures are not self-reproducible. `scripts/gen_fixtures_model.py` now pins `highest` (a bit-exact no-op on CPU) and records `jax_platform`/`jax_matmul_precision`; `tests/test_model_parity.py` refuses any fixture that is not fp32-exact. (N005; results/N005-parity-bisect/gpu_902051.log, gpu_*.npz vs gpuhi_*.npz) {cites:2}

## Refuted
- R001 <- K013: `default_vp_scaled`/`multimotif_vp` model-forward parity (real checkpoints, real pinned neighbour draws, same harness that gives `default_vp` 0.00002 A) is measurably worse and NOT understood: max coord dev 0.0059 A / 0.037 A respectively (~300x / ~1800x looser), several channels over the 2e-5 tolerance budget, yet aatype (downstream argmax) matches EXACTLY in both cases and the `multimotif_vp` `MotifAdapterDiffusionBlock`/pair-feature translation was checked line-by-line against NSB and is faithful. Working hypothesis (not confirmed): fp32 tie-flips in the discrete top-k neighbour selection, chained across the 6 trunk blocks within ONE forward pass — the same mechanism as the already-documented 81-step sampler chaos, just operating on 6 internal steps instead of 81. (N004; results/N004-porting-gaps/task1_parity_{default_vp_scaled,multimotif_vp}.txt) {cites:1}
  REFUTED by N005: the gap was never a property of these two configs. Both fixtures were generated on an H100 (`results/N004-porting-gaps/gen_fixtures_task1.sbatch`, `--partition=h100 --gres=gpu:h100:1`) where XLA uses TF32 for fp32 dots; `default_vp` itself reproduces the identical failure signature when regenerated on a GPU (out_pos 5.98e-03 A). Against a CPU JAX run the torch port matched to 9.27e-06 A at every block-0 tensor. Regenerated on CPU: default_vp_scaled 0.00589 -> 0.00002 A, multimotif_vp 0.03694 -> 0.00020 A. The N004 framing "the only difference is the weights ... points at the weights themselves" is also refuted - the weights were never involved. (N005; results/N005-parity-bisect/)
